# خطة مشروع نسق - تطبيق Flutter

## الهدف

مشروع نسق هو تعديل لفلو تطبيق نيرو أكاديمي الأصلي، مع الاستفادة الانتقائية من تحسينات برانش شهاب تك، بدون إدخال جزء الويب Next في هذه المرحلة.

التطبيق سيظل يحتوي على:

- أدمن.
- مدرس.
- طالب.

لكن الفلو الأساسي سيتغير بحيث يختار الطالب المدرس، ثم يتم عرض بيانات التطبيق وثيمه ومحتواه بناء على المدرس المختار.

## نطاق العمل

داخل النطاق:

- تطبيق Flutter فقط.
- Supabase schema جديد.
- حذف أو تعطيل الدفع القديم.
- إضافة نظام طلبات دفع لكل مدرس.
- فلترة بيانات الطالب والمدرس حسب `teacher_id`.
- إضافة ثيم لكل مدرس.
- الحفاظ على داشبورد المدرس الحالية مع تعديل مصادر البيانات.
- الحفاظ على الأدمن وتطوير دوره العام.

خارج النطاق حاليا:

- موقع Next.
- صفحات ويب منفصلة لكل مدرس.
- Subdomains أو routing للويب.
- أي تحسينات خاصة بالويب فقط من برانش شهاب.

## المرحلة 0: تجهيز البرانش

1. التأكد أن الشغل الحالي على `sehap-edits` محفوظ.
2. إنشاء برانش جديد من `master`:

```bash
git checkout master
git pull origin master
git checkout -b nasaq-app
```

3. اعتبار `master` هو الأساس لأنه يحتوي على النظام الكامل: أدمن، مدرس، طالب.
4. عدم عمل merge كامل من `sehap-edits`.
5. نقل التحسينات المفيدة فقط من برانشات شهاب بشكل انتقائي.

## المرحلة 2: تصميم قاعدة البيانات الجديدة

إنشاء سكربت جديد:

```text
database_scripts/nasaq_schema.sql
```

الجداول الأساسية المقترحة:

- `profiles`
- `teachers`
- `teacher_settings`
- `teacher_themes`
- `student_teacher_links`
- `courses`
- `lessons`
- `enrollments`
- `payment_requests`
- `student_progress`
- `notifications`

### profiles

جدول المستخدمين العام:

- أدمن.
- مدرس.
- طالب.

### teachers

سجل خاص لكل مدرس، مربوط بحساب في `profiles`.

### teacher_settings

إعدادات المدرس العامة داخل التطبيق.

### teacher_themes

ثيم وهوية المدرس:

- اللون الأساسي.
- اللون الثانوي.
- لون الخلفية.
- رابط الشعار.
- اسم العرض.
- نص ترحيبي اختياري.

### student_teacher_links

جدول ربط الطالب بالمدرس.

الاقتراح: دعم أكثر من مدرس للطالب، مع وجود مدرس نشط واحد داخل التطبيق.

### courses

يجب أن تكون الكورسات مربوطة بـ `teacher_id`.

### lessons

الدروس مربوطة بالكورسات، ومن خلالها يتم معرفة المدرس.

### enrollments

اشتراكات الطلاب في كورسات مدرس معين.

### payment_requests

بديل الدفع القديم:

- `id`
- `student_id`
- `teacher_id`
- `course_id`
- `amount`
- `status`
- `payment_method`
- `proof_image_url`
- `student_note`
- `teacher_note`
- `created_at`
- `reviewed_at`

الحالات المقترحة:

- `pending`
- `approved`
- `rejected`
- `cancelled`

### student_progress

تقدم الطالب داخل الدروس والكورسات، ويجب أن يكون قابلا للفلترة حسب المدرس.

## المرحلة 3: RLS وسياسات الأمان

يجب أن تكون الحماية في قاعدة البيانات، وليس في الواجهة فقط.

القواعد المطلوبة:

- الطالب يرى بياناته فقط.
- الطالب يرى المدرسين المرتبط بهم فقط.
- الطالب يرى كورسات المدرس المختار فقط.
- الطالب يرى طلبات الدفع الخاصة به فقط.
- المدرس يرى كورساته فقط.
- المدرس يرى طلابه فقط.
- المدرس يرى طلبات الدفع الخاصة به فقط.
- المدرس يرى تقدم طلابه فقط.
- الأدمن يرى كل شيء.

## المرحلة 4: حذف الدفع القديم

تحديد كل أماكن الدفع الحالية:

- Payment service.
- Payment screens.
- Checkout screens.
- Subscription logic.
- Payment webhooks إن وجدت.
- جداول الدفع القديمة.

ثم تنفيذ التالي:

1. حذف أو تعطيل شاشة الدفع المباشر.
2. استبدال الشراء المباشر بطلب دفع.
3. الطالب يرسل طلب دفع مرتبط بمدرس وكورس.
4. المدرس يراجع الطلب من داشبورده.
5. عند الموافقة يتم إنشاء enrollment للطالب.
6. عند الرفض لا يتم فتح الكورس.
7. الأدمن يمكنه رؤية كل الطلبات للمراقبة.

## المرحلة 5: Teacher Context داخل التطبيق

إضافة طبقة مركزية مسؤولة عن المدرس المختار.

أسماء مقترحة:

- `TeacherContext`
- `SelectedTeacherProvider`
- `TeacherThemeService`

المسؤوليات:

- حفظ المدرس المختار.
- تحميل بيانات المدرس.
- تحميل ثيم المدرس.
- توفير `teacherId` لكل services.
- إجبار صفحات الطالب على استخدام المدرس الحالي.
- توفير fallback theme عند غياب إعدادات المدرس.

الفلو:

1. الطالب يعمل login.
2. التطبيق يتحقق من وجود مدرس مختار.
3. إذا لم يوجد مدرس مختار، ينتقل إلى شاشة اختيار المدرس.
4. إذا يوجد مدرس مختار، يتم تحميل بياناته وثيمه.
5. الطالب يدخل إلى dashboard.

## المرحلة 6: تعديل فلو الطالب

الفلو الجديد:

1. Login أو Register.
2. Complete profile إذا كان مطلوبا.
3. Select Teacher.
4. Load Teacher Theme.
5. Student Home.

صفحات الطالب المطلوبة:

- شاشة اختيار المدرس.
- الصفحة الرئيسية حسب المدرس.
- كورسات المدرس.
- تفاصيل الكورس.
- إنشاء طلب دفع.
- متابعة حالة طلبات الدفع.
- كورساتي.
- تقدمي.
- حسابي.
- تغيير المدرس النشط.

ملاحظة: الأفضل دعم ارتباط الطالب بأكثر من مدرس من البداية، حتى لو كان الاستخدام الأولي يركز على مدرس نشط واحد.

## المرحلة 7: تعديل داشبورد المدرس

المدرس سيستخدم نفس الداشبورد الموجودة قدر الإمكان.

التعديلات المطلوبة:

- فلترة الكورسات حسب المدرس الحالي.
- فلترة الطلاب حسب المدرس الحالي.
- عرض طلبات الدفع الخاصة بالمدرس.
- الموافقة أو رفض طلبات الدفع.
- عرض تقدم الطلاب داخل كورسات المدرس.
- إضافة صفحة إعدادات الثيم.

صفحات مطلوبة أو محتملة:

- طلبات الدفع.
- إعدادات الثيم.
- طلابي.
- تقدم الطلاب.
- إدارة كورساتي.

## المرحلة 8: تعديل الأدمن

الأدمن يظل موجودا لإدارة ومراقبة المنصة.

صفحات الأدمن المقترحة:

- كل المدرسين.
- إنشاء أو تعطيل مدرس.
- ربط حساب مستخدم كمدرس.
- كل الطلاب.
- كل الكورسات.
- كل طلبات الدفع.
- إحصائيات عامة.
- إعدادات عامة للتطبيق.

الأدمن لا يكون جزءا من فلو الدفع اليومي لكل مدرس، لكنه يملك رؤية عامة وتدخل إداري عند الحاجة.

## المرحلة 9: الثيم والهوية

النسخة الأولى من الثيم يجب أن تكون بسيطة وقابلة للتوسع.

الحقول المقترحة:

- `primary_color`
- `secondary_color`
- `background_color`
- `logo_url`
- `display_name`
- `welcome_text`

داخل Flutter:

- تحميل الثيم بعد اختيار المدرس.
- تطبيق الألوان على `ThemeData`.
- استخدام fallback theme عند عدم وجود ثيم مخصص.
- عدم كسر تجربة الأدمن والمدرس عند غياب الثيم.

## المرحلة 10: نقل تحسينات شهاب المفيدة

بعد إنشاء برانش `nasaq-app` من `master`، تتم المقارنة مع `sehap-edits`:

```bash
git diff master..sehap-edits
```

ما يتم نقله:

- bug fixes.
- تحسينات Flutter المشتركة.
- إصلاحات Supabase client.
- تحسينات UI مناسبة للتطبيق.
- services أو helpers مفيدة.
- أي شاشة مكتملة أفضل من نسخة `master`.

ما لا يتم نقله:

- حذف الأدمن.
- منطق دفع قديم غير مناسب.
- تعديلات خاصة باسم شهاب تك.
- سكربتات قاعدة بيانات غير منظمة.
- أي تعديلات تخص Next web فقط.

## المرحلة 12: الاختبار

سيناريوهات الاختبار الأساسية:

### طالب جديد

1. يسجل حساب جديد.
2. يختار مدرس.
3. يرى كورسات المدرس فقط.
4. يرسل طلب دفع لكورس.
5. يرى حالة الطلب.

### مدرس

1. يدخل لحسابه.
2. يرى كورساته فقط.
3. يرى طلبات الدفع الخاصة به فقط.
4. يوافق على طلب دفع.
5. يتأكد أن الكورس ظهر للطالب.

### طالب مع أكثر من مدرس

1. يختار مدرس أول.
2. يرى ثيم ومحتوى المدرس الأول.
3. يبدل إلى مدرس آخر.
4. يرى تغير الثيم والمحتوى.

### أدمن

1. يرى كل المدرسين.
2. يرى كل الطلاب.
3. يرى كل طلبات الدفع.
4. يستطيع تعطيل أو إدارة المدرسين.

## ملاحظات تنفيذية

- لا يتم عمل merge كامل من `sehap-edits`.
- لا يتم حذف الأدمن في مشروع نسق.
- الدفع يكون طلب دفع لكل مدرس، وليس دفعا عاما للمنصة.
- كل query تخص الطالب أو المدرس يجب أن تأخذ `teacher_id` في الاعتبار.
- RLS يجب أن تمنع الوصول الخاطئ حتى لو حدث خطأ في الواجهة.
- جزء الويب Next يؤجل لمرحلة منفصلة.
